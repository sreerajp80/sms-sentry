# Plan: Full P2P sync (host → fresh phone)

**Status:** completed

## Goal / context

Today the P2P sync sends only the raw message fields (`sender`, `body`, `timestamp`,
`category`, `simId`) and the client **re-classifies** everything on its side. That means the
client can end up with different categories, and it loses filter rules, manual reminders,
reminder settings (recurrence / alert on-off), and scheduled messages.

The user wants the P2P sync to copy **everything that can be copied** so a **fresh phone**
becomes a faithful clone of the host. Because the target is a fresh (empty) phone:

- Direction stays **one-way** (host → client), as today.
- **Scheduled (future-send) messages are included** (the user asked for this).
- Conflicts resolve as **host overwrites** — but on a fresh phone there are no conflicts, so
  this only matters if the sync is run twice; we keep it robust and idempotent.

## What syncs vs. what cannot (device-specific)

**Synced (host → client):**

- `messages`: `sender`, `body`, `timestamp`, `category`, `simId`, `isBlocked`, `isRead`,
  `type` (inbox/sent), `isMms` (flag only), `status`.
- `filter_rules`: `type`, `value`, `targetCategory`.
- `finance_transactions`: `bankName`, `amount`, `isCredit`, `balance`, `timestamp`
  (re-linked to the local message).
- `reminders`: `sender`, `title`, `body`, `dueDate`, `isSyncedToCalendar`, `recurrence`,
  `alertEnabled` (re-linked to the local message).
- `scheduled_messages`: `recipient`, `body`, `simId`, `scheduledTime`, `createdAt`
  (alarm re-armed on the client).

**NOT synced — device/provider-specific, cannot be carried across phones:**

- `SMSMessage.systemId` — row id in the host's `content://sms|mms` provider. Meaningless on
  another phone. Left `null` on the client.
- `SMSMessage.threadId` — the host provider's thread id. Left `null`; client falls back to
  grouping by sender.
- `SMSMessage.attachmentUri` — `content://` / file URIs to the host's local MMS media. The
  media blobs are not transferred over this text channel, so the URIs would dangle. Left
  `null` (the `isMms` flag and text body still cross; media does not).

Key design choice: the client **preserves the host's classification** (it does *not*
re-classify). Category, finance rows, and reminders are copied verbatim and re-linked, so the
fresh phone mirrors the host exactly regardless of rule differences.

## Wire protocol (breaking change — both phones need this build)

Replace the flat JSON array with a versioned object:

```json
{
  "v": 2,
  "messages":  [ { "idx":0, "sender":"", "body":"", "timestamp":0, "category":"",
                   "simId":1, "isBlocked":false, "isRead":false, "type":1,
                   "isMms":false, "status":0 } ],
  "rules":     [ { "type":"KEYWORD", "value":"", "targetCategory":"" } ],
  "finance":   [ { "msgIdx":0, "bankName":"", "amount":0.0, "isCredit":false,
                   "balance":0.0, "timestamp":0 } ],
  "reminders": [ { "msgIdx":0, "sender":"", "title":"", "body":"", "dueDate":0,
                   "isSyncedToCalendar":false, "recurrence":"NONE", "alertEnabled":true } ],
  "scheduled": [ { "recipient":"", "body":"", "simId":1, "scheduledTime":0, "createdAt":0 } ]
}
```

`finance[].msgIdx` / `reminders[].msgIdx` index into `messages[]` (the stable cross-device
link, since row ids differ per phone). A reminder with no parent message uses `msgIdx = -1`.
The crypto/handshake (salt → GCM `HELLO_SYNC` → `ACCEPT_SYNC` → encrypted payload) is
**unchanged**; only the plaintext payload shape changes.

## Notes / non-goals

- **No DB schema change** — no new columns or entities, so no `SmsDatabase` version bump and
  no migration.
- **No Gradle/dependency changes.**
- This is a **breaking wire-protocol change**: a `v:2` client cannot read a `v:1` host and
  vice-versa. Both phones must run this build. (The sync was already documented as breaking
  across builds.)
- MMS media is not transferable over the current text/JSON socket; only the `isMms` flag and
  the text body cross. Transferring media blobs would be a separate, larger change.
- Two-way merge is **out of scope** (kept one-way per the decision).
